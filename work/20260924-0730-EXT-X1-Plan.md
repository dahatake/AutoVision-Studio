## 2. 原因の調査の手順（E2）

- 条件の固定:
  - 同時に動かす process: 計画 §4.2 の `lock:perf-host` のとおり、各回の前に、ほかの lane のすべてのコマンド（vitest、typecheck、`npm run verify:docs`、grep など）と書込みが終わるのを待つ。1 回の実行を始めてから、すべての vitest の process が終わるまで、ほかの lane のコマンドと書込みを新しく始めない。各回の前の `Get-Process node -ErrorAction SilentlyContinue` の件数は記録として残す（lock の代わりではない）。
  - vitest の worker 数: `--maxWorkers=19`（この host の論理 CPU 20 から 1 を引いた値）を明示する。集約 `npm test` の実行時の worker 数は記録されていないため、同じ値だとは主張しない。
  - npm 12.0.0 を PATH の先頭に置く（Gate 2 計画 §8.0 の `NPM12`）。
- コマンド（失敗した 7 file だけをまとめて実行）:

```powershell
$env:PATH = $env:LOCALAPPDATA + '\npm-12.0.0;' + $env:PATH
& .\node_modules\.bin\vitest.cmd run --maxWorkers=19 src/main/data/copy-source.test.ts src/main/data/import-files.test.ts src/main/data/import-python.test.ts src/main/data/import-repository.test.ts src/main/data/import-service.test.ts src/main/jobs/job-service.test.ts src/main/jobs/worker-supervisor.test.ts
```

- 回数の上限: 通常に終わった測定を **3 回**（測定の前に固定する。2400 計画 §17 の規則 4）。結果によって回数を増やさない。
- 各回の手順（`$n` は回の番号。1 回ごとに別の shell で実行し、raw log の進みを監視する）:

```powershell
$n = 1  # 回の番号（1、2、3。停止の後の再試行は同じ番号）
$env:PATH = $env:LOCALAPPDATA + '\npm-12.0.0;' + $env:PATH
$raw = 'work\20260924-0730-EXT-X1-ExecutionRecord.raw.log'
$files = 'src/main/data/copy-source.test.ts', 'src/main/data/import-files.test.ts', 'src/main/data/import-python.test.ts', 'src/main/data/import-repository.test.ts', 'src/main/data/import-service.test.ts', 'src/main/jobs/job-service.test.ts', 'src/main/jobs/worker-supervisor.test.ts'
"run $n start $(Get-Date -Format o) node_processes=$(@(Get-Process node -ErrorAction SilentlyContinue).Count)" | Add-Content $raw
& .\node_modules\.bin\vitest.cmd run --maxWorkers=19 @files *>&1 | Add-Content $raw
"run $n exit=$LASTEXITCODE end $(Get-Date -Format o)" | Add-Content $raw
```

- 記録: 各回の `run <n> exit=<code>` の行、所要時間（vitest の `Duration` の行）、失敗した test 名（`FAIL` の行）、実行前の node process の件数。全出力は `work/20260924-0730-EXT-X1-ExecutionRecord.raw.log` に残す。
- 停止: raw log の出力が 10 分以上進まない場合は、その回の shell を process ID を指定して止め（`run <n> exit=` の行は書かれない）、その回を「停止」として記録する（停止の操作の側で raw log に `run <n> stopped reason=no-progress pid=<PID>` の行を加え、vitest 自身の失敗の exit と区別する）。停止の後、同じ条件での再試行は 1 回だけ行う（2400 計画 §17 の規則 3）。再試行も停止した場合は、E2 をそこで終え（残りの回は行わない）、原因未確定として扱う。

## 3. file ごとの修正ノードの形

- 原因が確定した場合にだけ、1 file 1 ノードで作る。確定とは、失敗が再現し、かつ次のどちらかがあることをいう。(a) どの分岐・条件が成立したかを示す観測（log の行）。(b) 固定した条件の下で 1 つの要因だけを変えた比較の結果。発生箇所（stack の `<path>:<行>`）しか分からない場合は確定としない。
- 各ノード: write set はその file と、原因の source の file だけ。500 行を超える file（`copy-source.test.ts` 1,066 行、`import-repository.test.ts` 721 行、`worker-supervisor.test.ts` 899 行）は、G2X-01a〜c と同じく編集する行範囲を列挙する（計画 §4.1 の E2 の行）。完了条件は、その file の vitest が exit 0。最後の修正ノードの後に、E2 と同じ条件で 7 file をまとめて 1 回実行する。
- test を弱めない（timeout の延長・test の skip・assert の緩和はしない。Gate 2 計画 L322）。
- 原因が確定しない場合は修正ノードを作らない。この場合 `EXT-X1` は計画 A3 の「原因未確定の経路」（`node fail --class contract`）で記録する。
