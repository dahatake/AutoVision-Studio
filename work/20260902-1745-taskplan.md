## 2. 別PCへ移すための必須チェックポイント

### 2.1 推奨方法: コミットしてremoteへpush

ソースPCで、秘密情報・モデルbinary・ローカルProjectが含まれていないことを確認してから実施する。

1. `git status --short --branch --untracked-files=all` で対象を再確認する。
2. `.env*`、証明書、秘密鍵、token、`vendor/models/`、ユーザー画像、Projectデータが追加対象にないことを確認する。
3. 次をstagingする。
   - `.gitignore`
   - `README.md`
   - `CONTRIBUTING.md`
   - `docs/`
   - `resources/models/manifest.json`
   - `resources/models/manifest.schema.json`
   - `work/20260902-1745-taskplan.md`
4. `git diff --cached --check` を実行し、エラー0件を確認する。
5. `git diff --cached --name-status` と差分本文を確認する。
6. A-07がレビュー未完であることを隠さず、例として `docs(A): baseline checkpoint; A-07 adversarial review required` のような意味のコミットを作る。
7. push権限と運用規則が許す場合だけ `main` を `origin` へpushする。
8. `<HANDOFF_COMMIT>` と実際のcommit SHAを本書の引継ぎ記録へ追記する。

### 2.2 remoteへpushできない場合

1. §2.1と同様にローカルcommitを作る。未コミットfileはGit bundleへ含まれないため、commitは省略できない。
2. `main` を含むGit bundleを作成する。
3. bundleと、そのSHA-256を別PCへ安全にコピーする。
4. 別PCでbundleをcloneまたはfetchし、`<HANDOFF_COMMIT>` をcheckoutする。
5. bundle転送後も署名秘密、モデルbinary、ユーザーデータは同じ媒体へ混在させない。

### 2.3 別PC側の復元確認

1. `main` をcheckoutする。
2. `git rev-parse HEAD` が `<HANDOFF_COMMIT>` と一致することを確認する。
3. `git status --short --branch` がcleanであることを確認する。
4. §1.4の重要ファイルhashを再計算する。
5. `docs/requirement-definition.md` が914行、113,025 bytes、SHA-256 `2f1c...052f` であることを確認する。
6. `resources/models/manifest.json` が `releaseStatus.ready=false`、`models=[]` であることを確認する。
7. hash不一致、欠落、予期しないbinaryがあれば実装を開始せず、ソースPCとの差分を解決する。

## 4. 全タスク共通の実行・敵対的レビュー手順

各タスクで次を省略しない。並列タスクも個別にこの手順を完了してからmainへ統合する。

1. **Context Packを読む**
   - 対象requirement ID
   - 依存ADRの該当節
   - `docs/implementation-plan.md`の対象行
   - 編集対象file全文
   - 直接import先/元と隣接test
2. **依存を確認する**
   - すべての依存taskが`VERIFIED`か確認する。
   - Gate未通過なら開始しない。
3. **1挙動だけ実装する**
   - タスク表にないfileをついでに変更しない。
   - production 1〜3、test 1〜2の上限を守る。
4. **対象testを作成・実行する**
   - 正常系だけでなく、要求に明記された境界・失敗系を含める。
   - 実行コマンド、OS、version、終了コード、結果を記録する。
5. **diagnosticsを確認する**
   - type、lint、editor diagnostics、対象testを確認する。
6. **独立した敵対的レビューを行う**
   - 実装担当とは別agent、別context、または別reviewerを使う。
   - 対象要求の未実装、要求外実装、YAGNI、入力境界、状態遷移、path traversal、IPC、ネットワーク、データ不変性、ライセンス断定、testの偽陽性を確認する。
   - 指摘にはfile/箇所、再現条件、期待値、根拠requirementを付ける。
   - 証明できない懸念は欠陥として断定せず「未確認」とする。
7. **レビューを反映する**
   - 確認できた指摘だけを同タスク内で修正する。
   - 仮説だけの予防コード、過剰ログ、汎用抽象化を追加しない。
8. **再検証する**
   - 対象test、diagnostics、指摘再現testを再実行する。
   - すべてCLOSEDになるまで後続taskを開始しない。
9. **証拠を保存する**
   - PR description/review commentを使える場合はそこへ記録する。
   - PRを使わない場合はtask commit本文へ、要求ID、test、review finding、修正、再検証、残blockerを記録する。
10. **状態を`VERIFIED`にする**
    - 実装だけ、testだけ、review前は完了扱いにしない。

推奨状態遷移:

`TODO → IN_PROGRESS → TESTED → ADVERSARIAL_REVIEW → FIXING → REVALIDATED → VERIFIED`

外部条件不足は`BLOCKED`とし、`VERIFIED`へ読み替えない。

### 4.1 並列実行のGit運用

- 出力fileが重ならず、依存が満たされたtaskだけを同じwaveで並列化する。
- 並列workerごとに一時branch/worktreeを作り、1 taskだけを担当させる。
- 各branchでtest・敵対的レビュー・修正・再検証を完了し、task IDを含むcommitを作る。
- integration担当がmainへ依存順にcherry-pickまたはmergeし、統合後testを再実行する。
- main統合後、一時worktreeとbranchを通常削除する。未マージcommitやdirty worktreeをforce削除しない。
- wave終了時にmain以外の一時branch/worktreeが不要なら0件へ戻す。
