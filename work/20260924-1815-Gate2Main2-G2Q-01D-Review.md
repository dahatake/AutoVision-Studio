- 対象: `spikes/models/assist-goldset-plan-detection.md`（検出 の gold set と判定基準の数値案。確定は所有者が行う。Gate 2 計画 `work/202609232120-RemainTaskExecutionPlan.md` §8.9）。
- 方法: 独立の rubber-duck agent（読み取りだけ）が、下書きの段階で 3 回レビューした。確認の範囲: 数値ごとの出典の実在と正しさ、要求 ID の実在、ノードの要求を超える追加の有無、所有者の判断 G2D-05 との整合、測定の後に基準を動かせる余地の有無。verify の条件（`work/20260924-1815-Gate2Main2-verify.ps1` 162〜180 行）は、同じ論理を下書きに適用して確かめた（6 見出しがそれぞれ 1 節、各数値行の後ろまたは次の行に根拠か「所有者の判断事項」）。

## 結果

- round 1 の指摘（blocking 1）: 最終品質（F1）を計算する最終 box の記録先が定義されていない。session の JSON Lines に box は無く、`accept`/`edit`/`reject` と C7 の sidecar からは最終 box を復元できない。反映で、matching を同じ item の中だけに限ることも明記した。
- round 2 の反映: 最終品質の入力を、各 session の後に製品で確定した Dataset Revision の manifest（FR-ANN-010、`src/main/data/revision-manifest.ts` 10〜40・204 行）と定め、session の JSON Lines の形式は変えない（`work/20260924-0730-EXT-41-Plan.md` §1）。`outcome` と sidecar から最終の値を推定しない。
- round 2 の指摘（blocking 1）: session と manifest の機械的な対応が未定義で、harness が別の revision を評価しうる。また、manifest の class は UUID で、名前は `schema` にある。
- round 3 の反映: 記録者が manifest を `<session file の stem>.revision.json` として複写し、SHA-256 を受け渡しメモに書く。harness（G2Q-02）は `--assisted-revision` / `--manual-revision` の明示入力で受け取り、SHA-256 を照合し、両 manifest の SHA-256 を出力する。「最新の revision」を探さない。照合は `items[].imageSha256`、class は同じ manifest の `schema` で名前へ解決する。item の欠落・重複・除外、`taskType` の違いは session の無効（fail-closed）。
- round 3: blocking 0。
