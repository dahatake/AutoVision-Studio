## 1. 要因 1: 別 thread の file descriptor を閉じる test（確定: 観測 (a)）

### 観測

`NODE_OPTIONS=--trace-warnings` で集約 vitest（`vitest.cmd run --maxWorkers=19`）を 1 回実行した（trace log 1 行目: 22:19:13 開始、exit 1、Test Files 4 failed | 117 passed）。Node が「この worker が開いていない fd を閉じた」ことを示す警告を、呼び出し元の stack とともに 2 件出した。

| trace log の行 | 警告 | 閉じた箇所 |
|---|---|---|
| 5〜8 | `File descriptor 6 closed but not opened in unmanaged mode` | `src/main/data/reference-source.test.ts:700`（teardown の `realClose(fd)`） |
| 9〜16 | `File descriptor 4 closed but not opened in unmanaged mode` | `src/main/data/import-files.test.ts:274`（mock の `realClose(fd)`）← 製品の `close()` の再試行 `src/main/data/import-files.ts:165` |

同じ回に、reference-source の `close-before-release` の test が `reference-source.test.ts:688`（閉じた後の `fstat(fd)` が EBADF で失敗することの確認）で「throw しなかった」として失敗した（trace log 83〜93 行）。閉じた番号が、別の thread に再利用されていたことを示す。

### 仕組み

- `pool: 'threads'` では、すべての test file が 1 つの process の worker thread で動き、fd の表を共有する。閉じた fd の番号は、ほかの thread がすぐに再利用できる（close(2): 閉じた fd は「may be reused」。man7.org の close(2) の DESCRIPTION と NOTES）。
- (A) `import-files.test.ts` の `close` 段階の mock（修正前の 273〜276 行）は、本物の `closeSync(fd)` で閉じた後に例外を投げていた。製品の `close()`（`import-files.ts:161-167`）は失敗時にもう 1 回 `closeSync(fd)` を呼び、mock はその番号を本物の close でもう一度閉じていた。別の thread が番号を再利用していれば、その thread の fd を閉じる（trace log 9〜16 行がこの経路）。
- (B) `reference-source.test.ts` の teardown（修正前の 694〜701 行）は「`fstat(fd)` が成功すれば `closeSync(fd)`」だった。製品が fd を解放した後に別の thread が番号を再利用していると、その thread の fd を閉じる（trace log 5〜8 行がこの経路）。
- (C) 「閉じた後の `fstat(fd)` が失敗すること」の確認（修正前の reference-source.test.ts 564・650・688 行、import-handlers.test.ts 224・240 行）は、別の thread が番号を再利用すると成功してしまい、test が誤って失敗する（trace log 83〜93 行）。
- 別の thread の fd を閉じられた test は、読み書きの失敗・timeout・404 などの形で失敗しうる。個々の失敗（例: trace log の image-protocol の 404）がどの fd の close によるかは観測していない。

### 修正（test だけ。製品は変えない）

| file | 変更 |
|---|---|
| `src/main/data/import-files.test.ts` | `close` 段階の mock は、解放した番号への製品の再試行を本物の close へ渡さず、`EBADF` の例外を返す（解放済みの fd を閉じ直したときの OS の結果を模す）。注入する失敗・製品の経路・確認する結果は変えない |
| `src/main/data/reference-source.test.ts` | 564・650・688 行の `fstat` による確認を、「本物の `closeSync(fd)` が正常に戻った（spy の `mock.results` の `type: 'return'`）」の確認に置き換えた。Node の `closeSync` は OS の close が成功した場合にだけ正常に戻るため、fd が解放されたことを、再利用の影響を受けずに確かめる。teardown は、最初の `openSync` が返した fd（`open.mock.results[0]`。途中の assert が失敗して `fd` の代入の前に終わった場合も対象にする）について、正常に戻った close が無い（=解放されていない）場合にだけ閉じる |
| `src/main/ipc/import-handlers.test.ts` | 224・240 行の `fstat` による確認を、同じ `mock.results` の確認に置き換えた |

確認: 3 file の vitest が exit 0（192 tests passed、22:31〜22:33）。`npm run typecheck` が exit 0。修正後の集約 `npm test`（verify log の run 1）で `closed but not opened` の警告は 0 件だった。

### 他の test の点検（同じ危険が無いこと）

`src` の test で `closeSync` を mock する箇所・手で閉じる箇所を検索した（`realClose\(|closeSync'\)\.mockImplementation|\.closeSync\([a-zA-Z]+\)`）。

- `copy-source.test.ts:331`・`:880`: 製品の再試行は、`fstat` でその fd が同じ file を指すことを確かめた場合だけ閉じる（`copy-source.ts:360-366`）。teardown（`:398`）は製品がまだ閉じていない自分の fd だけを閉じる。危険は無い。
- `diagnostic-export.test.ts:221`: 製品は再試行しない。
- `backup.test.ts:393`、`scan-artifact.test.ts:251`: 自分で開いた fd / handle を 1 回だけ閉じる。

### 記録だけ行う所見（修正しない）

製品の `import-files.ts:161-167` と `reference-access.ts:482-487` は、close の失敗の後に同じ fd へもう 1 回 `closeSync` を呼ぶ。close(2)（man7.org、NOTES）は「失敗の後に close を再試行するのは誤りで、別の thread が再利用した fd を閉じることがある」と書く。ただしこれは Linux の記述で、本製品の対象の Windows（CRT の fd）で close の失敗後に番号が解放されるかは確認していない。`closed but not opened` の警告と reference-source の失敗の原因は mock・teardown の二重 close（上の A）であり（集約 test のほかの失敗の原因ではない）、製品の変更は EXT-X1 の範囲外のため、所見として残す。

## 2. 残りの失敗: 時間に依存する test（原因は未確定）

### 観測

要因 1 の修正後の集約 `npm test`（worker 数は既定。vitest 4.1.11 の run の既定は `availableParallelism - 1` = 19: `node_modules/vitest/dist/chunks/cli-api.CnMVyzaz.js:3832-3838`）の 1 回目は exit 1（verify log: Test Files 6 failed | 112 passed (118)、Tests 16 failed）。失敗はすべて時間切れだった: `Test timed out in 20000ms` / `30000ms`（verify log 110・123・136・149・181・194・208 行）、`JOB04 native test deadline exceeded`（165 行）、`[vitest-pool-runner]: Timeout waiting for worker to respond`（226〜252 行）。このうち copy-source は単独では失敗しなかった（`work/20260924-0730-VitestFailure-c.md`: 0/5）。ほかの 5 file（index、project-handlers、worker-supervisor、project-move.review、project-service）の単独の結果は取っていない。2 回目の途中で止めた（verify log の `run 2 stopped` の行）。

### 比較 1: worker 数（19 → 50%）

仮説「worker 数 19 による過負荷」を、worker 数だけを `--maxWorkers=50%`（10）に変えた集約 `npm.cmd test` で比べた（回数は事前に 3 回と固定。workers50 log）。1 回目（22:53〜23:12）は exit 1（Test Files 8 failed | 113 passed (121)、Tests 17 failed。workers50 log 275〜276 行）で、失敗の種類は既定の worker 数の場合と同じだった（`Test timed out`、`JOB04 native test deadline exceeded`（210 行）、reference の読出しの失敗による `expected 404 to be 200`（139 行）、`expected 1 to be 2`（reference-image、171 行））。3 回すべての exit 0 が成り立たなくなったため、2 回目の途中で止めた（workers50 log の `run 2 stopped` の行）。**worker 数を減らしても、すべて通る回は観測されなかった。** ただし外の負荷が変わる中の比較で、固定した条件の 1 要因比較ではないため、仮説は否定ではなく未確定とする（敵対的レビューの指摘）。

### 観測: host の CPU 使用率

この作業で test を動かしていない状態（この作業の process は短い command だけ）で、host の CPU 使用率（`\Processor(_Total)\% Processor Time`）は 23:16 の手動の測定で 82〜88%（2 秒ごとの 3 回）、23:20〜23:50 の間 52.8〜88.7% だった（`work/20260924-2215-EXT-X1-hostload.raw.log`、30 秒ごとの平均 61 件）。負荷の元は、この作業の外の process（別の repository の `dotnet test`・MSBuild・`VBCSCompiler`、`pytest` など。23:16 の `Win32_Process` の command line で確認）で、本作業では止めない（共有の環境のため）。E2 の成功の 3 回（14:08〜14:11、7 file、各 47〜58 秒）と比べ、失敗した回の file の所要時間は大きい（workers50 log: `project-service.test.ts` 265 秒、`import-service.test.ts` 221 秒）。

### 比較 2: CPU の負荷を加えるかどうか（事前に固定した計画）

### 比較 3: test の process が使える CPU の数（事前に固定した計画）

比較 2 は負荷を加える process の不具合で無効だった。共有の host の他の作業に負荷をかけないように、要因を「test の process が使える論理 CPU の数」に替える。

- 固定する条件: E2 の 7 file、`--maxWorkers=19`、同じ code、preload なし。vitest は `node node_modules/vitest/vitest.mjs run ...` で起動する（`vitest.cmd` と同じ入口）。
- 変える 1 要因: vitest の process の `ProcessorAffinity` を、A では変えない（20 個）、B では論理 CPU 4 個（`0xF`）に限る。worker は同じ process の thread で、子 process（`mountvol.exe`・JOB04 の native の worker）は affinity を受け継ぐ。A・B・A・B の順に 4 回（回数は増やさない）。
- 判定: B の 2 回がともに exit 非 0 で、失敗の種類が集約の失敗と同じ種類（時間切れ・`JOB04` の deadline・`WORKER_*TIMEOUT`・volume の probe の失敗）だけであり、かつ A の 2 回の失敗の test の数の合計が B の 2 回の合計より少ない場合に、「CPU の不足で時間の上限を超える」を確定とする。それ以外は未確定とする。
- raw log: `work/20260924-2215-EXT-X1-affinity-compare.raw.log`。

結果: A は 2 回とも exit 0（raw log 11 行・96 行。前の CPU 使用率 44%・100%）、B は 2 回とも exit 1（85 行・125 行）。失敗の test の数は A が合計 0、B が合計 4（2 回目 3 件: 23 行、4 回目 1 件: 105 行）。B の失敗は、`copy-source.test.ts` の `Test timed out in 30000ms`（31 行・113 行）と、`worker-supervisor.test.ts` の JOB04 の native の test で `kill` が呼ばれた 2 件（`expected "kill" to not be called at all`: 44 行、`times out finitely without promoting ACK=true to success` の `expected "kill" to be called +0 times, but got 1 times`: 71 行）だった。`kill` の 2 件は、判定に列挙した種類に入っていない（最初の集約 `npm test` にも同じ message の失敗はある: `work/20260924-0730-EXT-X1-npmtest.raw.log` 380〜381 行・407〜408 行）。判定は列挙した種類「だけ」を条件にしていたため、後から種類を広げずに、**比較 3 は判定の条件を満たさず、未確定とする**。また、affinity は process の起動の直後に設定したため、起動の最初の短い時間は 4 個に限られていない（敵対的レビューの指摘）。

### 比較 4: test の process が使える CPU の数（比較 3 の設計の訂正。事前に固定した計画）

- 比較 3 からの変更は次の 2 点だけ。(1) affinity を、vitest を起動する前の `pwsh` 自身に設定する。Windows では process の affinity は子 process に受け継がれる（Microsoft Learn「SetProcessAffinityMask function」の Remarks: "Process affinity is inherited by any child process or newly instantiated local process."）ため、`vitest.cmd`・node・その子 process は起動の時から同じ affinity になる。A の `pwsh` には設定しない。(2) 判定に、JOB04 の native の test の `kill` の呼び出しの回数の assert の失敗を加える（事前に固定する）。
- 固定する条件: E2 の command（`vitest.cmd run --maxWorkers=19`、7 file）、npm 12.0.0、同じ code、preload なし。A・B・A・B の順に 4 回（回数は増やさない）。B は論理 CPU 4 個（`0xF`）。
- affinity の確認: 各回の実行中に 5 秒ごとに、その回の開始の後に作られ、command line に `AutoVision-Studio` を含む node の process の affinity を記録する。B ではすべて 15、A ではすべて 1048575 であることを判定の前提にする（違う値があれば無効）。
- 判定: B の 2 回がともに exit 非 0 で、各失敗が次の種類のどれかであり（`Test timed out in`、`JOB04 native test deadline exceeded`、`WORKER_TIMEOUT` / `WORKER_CLOSE_TIMEOUT` の期待との違い、`reason: 'unsafe'`、`JOB04 real native Node transport` の test の `kill` の呼び出しの回数の assert）、かつ A の 2 回の失敗の test の数の合計が B の 2 回の合計より少ない場合に、「test の process が使える CPU が足りないことは、集約と同じ種類の失敗を起こす十分な条件である」を確定とする。それ以外は未確定とする。
- raw log: `work/20260924-2215-EXT-X1-affinity4.raw.log`。

結果: **判定の条件を満たさず、未確定**。exit は A 1 回目 1（raw log 46 行）、B 2 回目 1（596 行）、A 3 回目 0（608 行）、B 4 回目 1（695 行）。失敗の test の数は A の合計 1（42 行）、B の合計 37（592 行 34 件、691 行 3 件）。起動の時の affinity は A 1048575、B 15（各回の `launcher_affinity` の行と、各回の終わりの行の `affinities=`。標本の node の process は各回 1 個で、JOB04 の子 process は短いため標本に入らなかった）。B の失敗の大部分は列挙した種類（`Test timed out in 30000ms`: 95・108・121・624 行、`WORKER_TIMEOUT` / `WORKER_CLOSE_TIMEOUT`: 158・202 行ほか、`JOB04 native test deadline exceeded`: 227 行）だったが、列挙に無い種類もあった: `JOB05A test deadline exceeded`（`job-service.test.ts:45`、173 行）、`expected null to be +0`（296 行）、`TypeError: Cannot read properties of undefined (reading 'closed')`（`worker-supervisor.test.ts:448`、576 行）。A の 1 回目の失敗（`bounds 'oversized unterminated stdout'` で `WORKER_OUTPUT_LIMIT` の期待に対し `WORKER_CLOSE_TIMEOUT`、11〜27 行、前の CPU 使用率 92%）は、CPU を限らなくても外の負荷の下で失敗が起きることを示す。

## 3. 結果

- 要因 1（確定: 観測 (a)）: `import-files.test.ts` の mock と `reference-source.test.ts` の teardown が、製品が閉じた fd を本物の `closeSync` でもう 1 回閉じ、別の thread が再利用した fd を閉じる危険があった（§1 の (A)・(B)）。また「閉じた後の `fstat(fd)` が失敗する」の確認は、番号が再利用されると誤って失敗しうる（§1 の (C)）。失敗が観測されたのは `reference-source.test.ts`（trace log 83〜93 行）で、`import-handlers.test.ts` は同じ形の確認を予防として直した。3 file の test を直した（EXT-X1-F1〜F3。§1）。製品は変えていない。
- 残りの失敗（時間切れ・`WORKER_*TIMEOUT` など）: **原因は未確定**（計画 §3 の「確定」を満たさない）。観測の事実は次のとおり。(1) worker 数を 10 に減らしても、すべて通る回は観測されなかった（比較 1。1 要因比較ではない）。(2) test の process の使える CPU を 4 個に限ると失敗は大きく増えた（比較 3: A 0 件・B 4 件、比較 4: A 1 件・B 37 件）が、どちらも事前に固定した判定の条件（列挙した種類「だけ」）を満たさなかった。(3) CPU を限らなくても、外の process で host の CPU 使用率が高い時に失敗が起きた（比較 2 の 1 回目、観測 2 の 1 回目、比較 4 の 1 回目。前の CPU 使用率 89.9%・100%・92%）。(4) volume の probe の `unsafe` の分岐は観測 2 では出なかった。
- 計画 §3 により、確定していない原因の修正ノードは作らない。test の時間の上限の延長・skip・assert の緩和もしない。JOB04 の test は本物の process と時計を使う設計である（`worker-supervisor.test.ts:91` の注記 "Observe the REAL spawn/kill/close, without substituting a process or clock."）ため、偽の時計に置き換える変更は test の意図を変える。
