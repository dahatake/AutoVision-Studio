# ATG Kit の限界・非保証事項

## 1. 設計に関する限界

1. **タスク分解の正しさは保証されない。** `E` と `W` の宣言が誤っていれば、スケジューラは誤った並列化を安全と判断しうる。意味的競合の検出率も高いとはいえない。
2. **外部副作用の exactly-once は保証できない。** 前提は at-least-once である。
3. **ノード成功率が低い場合、有界リトライでは完走できない。** 失敗率が高い条件では、実行が中断しうる。
4. **並列化が無効なタスクが存在する。** ATG はその事実を検出して報告するが、解決はしない。
5. **本番・データ集約・安全重要領域における証拠は弱い。** これらは既定で自動化対象から外す立場をとる。
6. **ATG 自体の実運用証拠が存在しない。** 提示するのは設計、公開実証、それらを支えるスケジューリングモデルのシミュレーションまでである。
7. **同一状態ディレクトリで複数実行を併走させてはならない。** `run begin` が書く `<state>.context.json` は実行ごとに上書きされる。耐久状態（sqlite3）は複数実行を保持できるが、このコンテキストは 1 つしか保持しない。併走させる場合は `--state` を実行ごとに分ける。
8. **状態ファイルはローカルディスクに置く。** sqlite3 はネットワークファイルシステム上での複数ホスト同時アクセスに対する保護を持たないため、破損しうる。

## 2. `atg node check-writes` の検出範囲（重要）

本コマンドは契約外書込みを検出する唯一の機構だが、次の範囲でしか機能しない。
**「違反が検出されなかったこと」を「違反がないこと」の証明として扱ってはならない。**

| 条件 | 検出可否 |
|---|---|
| `--base` 以降に変更された追跡済みファイル | 検出する |
| 新規作成された未追跡ファイル | 検出する（`git ls-files --others --exclude-standard` を併用） |
| `.gitignore` で除外されたファイル | **検出しない**（`--exclude-standard` のため）。無視対象への書込みは別途確認が必要 |
| `--repo-dir` で指定した作業ツリー以外での変更 | **検出しない**。ノード専用 worktree を使う場合は `--repo-dir` にその worktree を渡す |
| `--repo-dir` に作業ツリーのルート以外（サブディレクトリ）を指定 | **検査せず拒否する**（exit 1）。`git diff` はリポジトリルート基準、`git ls-files --others` はカレントディレクトリ基準でパスを返すため、基準が食い違って違反を見逃す |
| リポジトリ外への書込み（絶対パス・親ディレクトリ等） | **検出しない**。git の管理範囲外であるため |

> **ATG 自身の状態ファイルについて**: `atg init` / `atg run begin` は状態ディレクトリ（既定 `.atg/`）に
> `.gitignore`（内容 `*`）を自動生成する。これは ATG 自身の耐久状態が契約外書込みとして
> 誤検出され、実際の違反が埋もれるのを防ぐためである。`--state` で既定以外の場所を指定した場合は、
> そのディレクトリを利用者側で git 管理対象から外すこと。

## 3. 本キットが計測しない受入条件

`atg report` の「機能受入条件」表のうち、次は**計測しない**（表にも「未計測」と表示する）。

- **実行中の人手介入回数**: ATG §13.1 は実行ログ中のプロンプト数を数えると規定するが、ATG CLI は実行ログを保持しない。
- **契約外書込み件数**: `atg node check-writes` をノードごとに実行した結果を利用者が集計する。
- **出典なし決定の件数**: `atg node finish` が handoff ごとに `decisions[].source_refs` を検査するが、レポートでは集計しない。

> **「必須ノードの終端被覆」は成功率ではない。** この指標は `succeeded` / `failed` / `blocked` を
> いずれも「終端した」として数える。したがって全ノードが失敗・ブロックされた実行でも 100% になりうる。
> レポートは内訳（`succeeded N / failed N / blocked N`）を必ず併記し、達成語を使わない。
> 実行が成功したかどうかは「総合結果」と「終端受入」の行で判断すること。

## 4. 作らないもの（N1〜N10）

以下は **v0.1 で実装しない**。

| ID | 作らないもの | 理由 |
|---|---|---|
| N1 | LLM 呼び出し・エージェント起動を行うランナー | 各面に既にエージェント実行基盤がある。ATG の差分は「同時実行してよいかの決定」であり、実行基盤の再実装は YAGNI。 |
| N2 | 統合ウェーブの**実行**（実際の `git merge` 実行・実際の影響範囲テスト実行の自動化） | 統合順序の決定・競合分類の**判定**は実装するが、実際のマージ・テスト実行はエージェント側に委ねる。ATG 自身が定義した規則の判定だけを実装し、規則を超えた自動実行機構は追加しない。 |
| N3 | 書込み集合 W(v) の自動推定 | ATG 技術文書 §15-1 自身が「今後の課題」とする。宣言方式で足りる。 |
| N4 | JSON Schema ファイル / jsonschema 依存 | 依存ゼロを維持する。検証は各モジュールの fail-closed な明示検査で行い、形式は `spec.md` に記述する。 |
| N5 | GUI / Web UI / サーバ / 外部データベース | 指示にない。ファイル 1 個（sqlite）で足りる。 |
| N6 | 秘密値スキャナ・独自の資格情報管理 | 契約に秘密を書かせない運用規則で足り、機構の新設は過剰。 |
| N7 | 失敗クラスの自動判定（transient / implementation / contract の推定） | 呼び出し側が明示的に渡す。推定は ATG §9.2「モデルの自由記述から差戻し先を推測しない」に反する。 |
| N8 | 設定オプション・環境変数・プラグイン機構・Strategy/Factory 等の抽象化 | 単発用途。必要になるまで作らない。 |
| N9 | PyPI / 外部レジストリへの公開 | 要求定義 FR-KIT-06 が「手動同期を前提とし、自動配布・外部レジストリへの公開を対象としない」と規定済み。 |
| N10 | 既存共有実装（`tools/skills/_kit/`・`_bootstrap/install.py`）への ATG 固有分岐の追加 | 共有実装を汚す。ATG は依存ゼロ・索引なしのため、それらの提供価値（venv・依存解決・索引生成）が無い。 |

## 5. ATG Kit が主張しないこと

- 既存手法に対する性能改善の程度
- 生成物の品質改善の程度
- コスト低減の程度
- 公開ベンチマークの解決率が ATG 運用時の成功率を予測すること
