# 計画フェーズの規約（分割判定・粒度・見積・完了条件）

> 本ファイルは ATG Kit の**フェーズ 1（計画）**の規約を定義する。
> フェーズ 2（実行判定）は [execution-loop.md](execution-loop.md)、計画からタスクグラフへの変換は [plan-to-graph.md](plan-to-graph.md) を参照する。
>
> 本ファイルはリポジトリ非依存である。特定のリポジトリの成果物フォーマット・CI・ラベル運用には依存しない。

---

## 0. 計画の作成手順

判定へ進む前に、次の順序で計画を組み立てる。

1. 受入条件（AC）と非対象を箇条書きで固定する。
2. 最小棚卸しを行う（対象一覧 / 根拠 / 検証手段）。
3. DAG を作成する（**ノード = 独立してレビュー可能な成果物 1 つ**）。
4. 各ノードへ、成果物 / 参照元 / 変更候補パス / 検証 / **参照ファイル数**（`context_size` 算定用）を付与する。
5. §3 の分割判定を機械的に実行し、結果を記録する。

参照ファイル数は手順 4 で数え上げた実数を使う。数えずに `context_size` を決めない。

---

## 1. `task_scope` と `context_size` の定義

| フィールド | 値 | 定義 |
|---|---|---|
| `task_scope` | `single` | 独立して検証可能な成果物が 1 つ |
| `task_scope` | `multi` | 独立して検証可能な成果物が 2 つ以上（分離可能） |
| `context_size` | `small` | タスク実行に必要な参照ファイル数が 1〜3 件 |
| `context_size` | `medium` | タスク実行に必要な参照ファイル数が 4〜8 件 |
| `context_size` | `large` | タスク実行に必要な参照ファイル数が 9 件以上、または単一ファイルが 500 行超 |

- 「独立して検証可能」とは、他の成果物の完成を待たずに exit code で合否を判定できることを指す。
- 参照ファイル数は**実際に読むファイル**を数える。読まないファイルを件数へ含めない。

---

## 2. 粒度の最低基準

以下に該当する場合は `task_scope` または `context_size` を見直す。

- 1 タスクで新規ファイルを 3 件以上生成する → `task_scope=multi` 候補
- タスク実行に必要な参照ファイルが 9 件以上 → `context_size=large`
- タスク実行に参照する単一ファイルが 500 行を超える → `context_size=large`
- 独立して検証・レビュー可能な成果物が 2 つ以上ある → `task_scope=multi`

1 ノードは「レビュー可能な成果物 1 つ」を単位とする。成果物が識別できないノードは粒度が粗すぎる。

---

## 3. 分割判定（機械的に実行 — エージェントの裁量なし）

以下の判定を**必ず**実行し、結果を計画文書の `## 分割判定` セクションへ記録する。

```
if task_scope == "multi":
    判定 = "SPLIT_REQUIRED"
    # ※ context_size が small/medium であっても SPLIT_REQUIRED。例外なし。
    → 計画のみを作成して終了する（実装ファイルの作成・変更を行わない）
    → ここで作業を終了する（実行へ進まない）

elif context_size == "large":
    判定 = "SPLIT_REQUIRED"
    → 上記と同じ

else:  # task_scope == "single" かつ context_size IN ("small", "medium")
    判定 = "PROCEED"
    → 実装に進んでよい
```

判定結果の記録には、次の 4 項目を必ず含める。

- `task_scope` の値
- `context_size` の値（参照ファイル数の実数を併記する）
- 判定結果（`PROCEED` / `SPLIT_REQUIRED`）
- 判定根拠（上記擬似コードのどの分岐に該当したか）

---

## 4. 分割判定の禁止事項

- `task_scope=multi` または `context_size=large` の場合に「分割不要」「1 バッチで実行可能」「まとめて実施」と判断すること。
- 「一括実行が合理的」「分割による品質低下リスク」等の理由で判定を覆すこと。
- エージェント個別の指示・役割記述を根拠に分割判定を緩和すること。
- 「ドキュメント生成のみ」「テンプレート適用のみ」等のタスク種別を根拠に緩和すること。
- 「完全な解を優先」「システム指示」「要件の達成」等を根拠に判定を覆すこと。
- 分割判定を行わずに実装へ進むこと。判定の記録がない計画は未完成として扱う。

---

## 5. 見積の最低基準

見積は次の 5 区分の合計を**分単位**で各ノードへ付与する。

| 区分 | 記号 | 内容 |
|---|---|---|
| 読込 | R | 入力ファイル・仕様の読み取り |
| 計画 | P | 手順の確定・依存の整理 |
| 実装 | I | 成果物の作成・変更 |
| 検証 | V | 検証コマンドの実行と失敗時の修正 |
| 予備 | F | 仕上げ・想定外の吸収 |

- 見積は**正の数値**とする。タスクグラフへ変換する場合、`duration` が正数を要求するため `0`・未記入のままでは変換できない（[plan-to-graph.md](plan-to-graph.md) §1）。
- 見積は上界指標（T1 / T∞ / 加速上界）の算出にのみ使う。**合否判定の根拠には使わない**。
- 実測と乖離した場合も、過去の見積を遡って書き換えない。

---

## 6. 完了条件（Definition of Done）の記述規約

- 各ノードに `## 完了条件` を置き、**非空**の記述を 1 行以上書く。空セクション・プレースホルダのみは未記載として扱う。
- 完了条件は「exit code またはファイル状態で判定できるもの」を 1 つ以上含める。自然言語のみの完了条件は置かない。
- 「動作すること」「品質が高いこと」のような主観的表現を判定条件にしない。
- 人間可読の `## 完了条件`（チェックボックス章）と、実行判定用の `verify_command` / `acceptance_command`（exit 0 で判定するコマンド文字列）は**別物**である。前者を 1 行のコマンドへ置き換えてはならず、後者へ自然言語を書いてもならない。
- 完了条件を exit code で判定できない場合は、**変換・実行へ進まず、完了条件の確定を先に行う**。

---

## 7. 直列／並列の判断

| 区分 | 該当する条件 |
|---|---|
| 直列（同一ノードへ寄せる） | 同じファイル・同じ公開 I/F（API / スキーマ / 設定キー）を高確率で触る／移行・互換・後戻り困難な変更／仕様確定→実装の依存が強い |
| 並列（別ノードへ分離） | 対象ディレクトリ・サービスが分離している／追記中心で衝突しにくい／検証の追加が独立している |

並列可否の最終判定は計画側では行わない。依存充足と書込み競合に基づく起動可否は ATG CLI が判定する（[execution-loop.md](execution-loop.md)）。計画側は**変更候補パスを各ノードへ宣言する**ところまでを責務とする。

共有すべき前提（契約・一覧・決定事項）は、レビューコメントではなく**ファイル**へ残す（後続が確実に読める形にする）。

---

## 8. 計画フェーズの非適用範囲

- 実装・テストの実行そのもの。
- 変更候補パスの自動推定。宣言されていないパスを推測で埋めない（[contract-authoring.md](contract-authoring.md) §2）。
- 完了条件が未確定なままのタスクグラフ化。
